# Движок пакетной классификации и приватности

## Назначение и границы

Движок принимает Excel/CSV, структурированные выгрузки и зарегистрированные
сканы, у которых нет надёжной разметки конфиденциальности. Названия полей,
форматы, вложенность и состав колонок могут изменяться. Задача — определить
чувствительность до публикации в аналитическом хранилище, применить разрешённые
преобразования и сохранить происхождение результата.

Подсистема детализирует конвейер приватности из
[целевой архитектуры](../Task2/architecture.md). Применяются классы
[стратегии защиты](../Task3/data-protection.md): `IDENTITY`, `CONTACT`, `HEALTH`,
`FINANCE`, `STAFF`, `SECRET`, `INTERNAL`. Классы могут сочетаться; `UNKNOWN`
обозначает неопределённость и требует строгого режима. Неразмеченные данные
разрешено сохранить только в защищённой зоне приёма, чтобы их обработать;
аналитика не получает к ней доступа.

На [C2](diagrams/classification-engine-c2.svg) движок рассматривается как
логическая подсистема платформы с несколькими самостоятельно развёртываемыми
приложениями и хранилищами. Это уточнение обобщённого контейнера конвейера,
а не диаграмма классов/внутренних функций одного приложения. Хранилища озера
и ClickHouse, общие идентификация, ключи, политики, каталог и аудит показаны
как зависимости платформы за границей движка.

## Контейнеры

| Контейнер | Ответственность | Данные и ограничения |
| --- | --- | --- |
| Приём пакетов, Java API | Проверка источника/цели, размера и формата, регистрация манифеста, приём файла | Источник аутентифицирован; пользовательская метка «не секретно» не считается доказательством. Макросы не исполняются |
| Закрытая зона приёма, S3 | Сохранение исходной версии и карантина | Разные области `incoming` и `quarantine`, шифрование, срок хранения, доступ только движку/оператору. Это не аналитическая зона |
| Координатор, Java-приложение | Разделение заданий, состояния, лимиты, повторы, выбор неизменяемой версии правил | Не обрабатывает большие тела в своей памяти; выдаёт задание с ограниченным временем владения |
| Реестр заданий и схем, PostgreSQL | Манифесты, хэши структуры, решения, версии, состояние публикации, контроль повторов | Не хранит образцы медицинского текста в свободных логах; метаданные также защищены |
| Анализаторы, Python-приложение / пул процессов | Разбор структуры, проверки по значениям, несколько детекторов, назначение тегов и неопределённости | Потоковая обработка, ограничения ресурсов, данные в закрытой среде; без внешних LLM/API |
| Преобразователи и валидаторы, Python-приложение / отдельный пул | Разрешённая проекция полей, псевдонимизация/агрегация, повторная проверка результата | Преобразования имеют версии. Обнаружение чувствительного остатка не переводится в предупреждение с публикацией |
| Интерфейс проверки, Web-приложение | Объяснение причин карантина, назначение класса/цели владельцем, исправление контракта | Только назначенный оператор видит необходимые фрагменты в изолированной сессии; решение фиксируется с идентификатором сотрудника и версией |
| Публикатор, Java-приложение | Запись проверенных наборов в нужный слой, контроль полной версии, фиксация происхождения и открытие разрешённого представления | Только публикатор имеет право активировать версию; аналитические роли не читают промежуточные таблицы или объекты |
| Сервис выдачи, Java API | Выбор опубликованного манифеста и проверка цели/роли до выдачи набора или агрегата | Читает только неизменяемую версию из манифеста; аналитические пользователи не получают прямых учётных записей хранилищ |

Один код анализатора обслуживает много работников; это один тип контейнера,
а не отдельная коробка на каждого работника. Число экземпляров — параметр
развёртывания. Приём, координатор и публикатор не дают внешнему клиенту
обойти проверку через прямую загрузку в ClickHouse.

## Пакет и изменения структуры

Обязательные сведения манифеста: `source_id`, версия исходного объекта,
`batch_id`, хэш содержимого, заявленная цель, владелец, число файлов,
версии контракта, политики и правил, ограничения хранения. Ожидаемое число строк
источник сообщает, если оно известно; фактическое число и структуру определяет
анализатор. Для скана единицей учёта является документ/страница.
Идентификатор пакета не является ID пациента.

Ключ повторной обработки — источник + версия объекта + хэш содержимого +
цель + версия контракта/политики + версия правил/преобразования.
Повтор доставки с тем же ключом возвращает
имеющееся состояние; новая версия правил создаёт новую проверяемую версию набора,
не молча заменяет старую. Хэш содержимого обнаруживает изменение файла,
но не доказывает, что структура и класс не изменились.

1. **Проверка приёма.** Проверить источник, цель и доступ; сохранить файл в `incoming`.
   Неподдерживаемый формат, опасная вложенность, превышение распакованного размера
   или времени разбора переводятся в карантин. Архивы и парсеры имеют пределы
   CPU/памяти; повреждённый файл не роняет остальных работников.
2. **Профилирование структуры.** Вычислить fingerprint — устойчивый отпечаток
   структуры: путь поля, нормализованное имя, тип, вложенность, массивность,
   допустимость пропуска, лист Excel и заголовок. Хранить также исходные имена.
   Не зависеть только от порядка колонок; одинаковая структура не означает
   одинаковое содержание.
3. **Сравнение с реестром.** Обнаружить добавление/удаление поля, смену типа,
   переименование, новые вложенные пути и изменение форматирования. Новый
   fingerprint не наследует разрешение публикации предыдущего.
4. **Анализ содержания.** Проверить значения всех полей, в том числе ранее известных.
   Для больших структурированных файлов проверки выполняются потоком по всем
   строкам. Выборка допустима для профилирования/приоритизации, но не единственный
   барьер публикации. Свободный текст требует отдельного разрешённого пути.
5. **Назначение класса.** Использовать совокупность признаков и контекст набора.
   Если обнаружено противоречие, нет надёжной классификации или изменился
   смысл поля — `UNKNOWN`, закрытый режим и проверка владельцем.
6. **Преобразование и контроль.** Применить разрешённые правила для цели,
   повторно проверить выход, обоснование и права целевого слоя; только затем
   публиковать целиком готовую версию.

Даже новый безобидный по виду столбец `note` может содержать диагноз и телефон.
Переименование `phone` в `field_17` не снимает тег `CONTACT`: анализ значений
продолжается. Изменение `age` на точную дату рождения усиливает идентифицируемость.
Удаление поля не отменяет классификацию старых объектов и истории копий.

## Как определяется класс

| Источник признаков | Что обнаруживает | Ограничение / действие |
| --- | --- | --- |
| Утверждённый контракт и контекст источника | Медицинский заказ/результат, кадровый и платёжный домен, цель использования | Метка источника может только усилить ограничения; неизвестная фактическая схема требует проверки |
| Имена, типы и пути полей | Контакты, идентификаторы, даты, признаки здоровья, массивы документов | Имена не являются единственным основанием; переименование и опечатки не делают поле публичным |
| Правила и словари по значениям | E-mail, форматы телефонов/идентификаторов, медицинские термины, секреты | Учитывать контекст и ошибки формата; регулярное выражение не узнает любую форму медицинского текста |
| Локальный NER-детектор | Сущности в тексте: человек, адрес, организация; NER — распознавание именованных сущностей | Отдельно оценивать качество на русскоязычных данных; низкая уверенность не означает отсутствие чувствительности |
| Межполевые связи и редкие комбинации | Совместная идентификация через возраст, филиал, дату, редкое исследование | Прямого идентификатора может не быть, а риск сохраняется; такой набор не объявляется анонимным |

Теги объединяются, а не выбираются большинством голосов. Медицинский контекст
источника задаёт `HEALTH` даже если по отдельной ячейке детектор ничего не нашёл.
Поле с секретом получает `SECRET` и запрещается к аналитической публикации.
Отпечаток схемы, теги, детекторы, версия правил и причина решения сохраняются
в реестре. Журнал не содержит найденное значение в открытом виде.

Сканы/OCR и свободный медицинский текст по умолчанию остаются закрытыми,
не публикуются в BI или наборы обучения автоматически. OCR — распознавание
текста изображения — может пропустить часть сведений; отсутствие найденного
ФИО не доказывает очистку файла. Для допуска нужны отдельный проверенный
процесс удаления сведений и решение владельца. Неопределённость на критичном
поле блокирует пакет; разрешённая часть может выйти только отдельным производным
пакетом с новым манифестом, чтобы не скрыть потерю строк или полей.

## Состояния, повторы и публикация

Основной путь: `RECEIVED → PROFILED → CLASSIFIED → TRANSFORMED → VALIDATED → PUBLISHED`.
Любой шаг может перевести пакет в `QUARANTINED` с причиной.
Временная техническая ошибка получает `RETRY_PENDING`; превышение лимита
повторов требует оператора и не разрешает публикацию. Решение оператора создаёт
новую версию обработки от сохранённого источника, а не вручную переписывает
статус в `PUBLISHED`.

Координатор выдаёт lease — право обработать задание на ограниченное время.
После сбоя срок истекает, другой работник продолжает обработку. Переход состояния
проверяет актуальную версию задания; поздний ответ первого работника не может
перезаписать новый результат. Промежуточные объекты сохраняются в пространстве
версии и не видны потребителю. Работник не выполняет произвольный SQL источника.

Публикатор сверяет полный манифест, выходную схему, контроль качества, цель,
права и аудит. Данные загружаются в закрытые временные объекты/таблицы,
после сверки активируется конкретная версия разрешённого представления.
Аналитические роли имеют доступ к опубликованным представлениям и разрешённым
объектам через сервис выдачи, а не ко всему пространству хранения.
Конкретный механизм: публикатор загружает неизменяемую версию во все целевые
объекты/таблицы, проверяет их и транзакционно активирует манифест в PostgreSQL.
Сервис выдачи выбирает только `PUBLISHED`-манифест, фиксирует одну версию для
всего чтения и обращается к объектам/таблицам этой версии. Поэтому незавершённая
загрузка не видна, а запрос не смешивает две версии. Доступ от обычных BI/ML-ролей
напрямую к S3/ClickHouse запрещён; собственная сервисная роль выдачи имеет
ограничение по опубликованным наборам и не читает Q0. Соединитель выбранного
BI-инструмента с этим интерфейсом проверяется при реализации; наличие штатного
подключения к произвольному API не предполагается.

Удаление/блокирование версии проверяется перед выдачей; отозванная версия
не доступна для нового запроса, даже если физический объект ещё хранится.
Длительная выгрузка проверяет действующее разрешение по блокам и может быть
остановлена. Сервис выдачи также масштабируется, ограничивает размер/частоту
выгрузок и записывает аудит чтения.

Сбой после загрузки и до активации оставляет предыдущую опубликованную версию
доступной; повтор завершает ту же версию, не добавляет строки второй раз.
Сбой после активации сверяется по манифесту и фактическому представлению;
статус нельзя определять только по ответу сетевого запроса. Недоступность
KMS (службы ключей), политики или надёжной записи аудита запрещает активацию.

## Слои аналитического хранения

Пакеты могут содержать разрешённые для конкретной цели конфиденциальные данные.
Поэтому один «обезличенный» бакет для всего озера недостаточен. Разделяются
физические/логические области, ключи, сервисные роли и опубликованные интерфейсы.

| Слой | Содержание | Доступ, защита и допуск |
| --- | --- | --- |
| Q0 — приём и карантин движка | Неразмеченный оригинал, повреждённые/неопределённые данные, ограниченные промежуточные объекты | Только приём, работники и назначенный оператор; отдельный ключ, запрет BI/ML; срок минимален для разрешённой проверки/повтора |
| L1 — классифицированный конфиденциальный слой озера | Только необходимые для утверждённой цели поля; например минимизированные псевдонимизированные сведения об исследованиях | Закрытая область и ключ; доступ по роли, цели, сроку и утверждённому набору. Таблица связи с реальным пациентом не выдаётся из клинического домена. Псевдонимизация не снимает `HEALTH` |
| L2 — проверенные наборы озера | Проекция без прямых идентификаторов, укрупнённые признаки, подавленные редкие группы; наборы для разрешённых экспериментов | Публикатор выдаёт конкретную версию. При остаточном риске набор сохраняет классы и режим L1; в L2 не переводится только по удалению ФИО |
| L3 — витрины ClickHouse | Проверенные агрегаты для управленческой отчётности по периоду, филиалу и типу услуги | BI-роль получает разрешённые агрегаты через сервис выдачи; малые группы/опасные сочетания не раскрываются; нет прямого соединения с клиническим `patient_id` |

Конфиденциальный L1 доступен не всем аналитикам: он требует отдельного
разрешения владельца на конкретную обработку. Общий BI использует L3,
ML (обучение моделей) по умолчанию — только допущенный L2. L1 не соединяется
со справочником пациентов или сырыми контактами через роль аналитика.
Публикация секретов запрещена во всех L1–L3. Шифрование хранения и передачи,
аудит чтений, сроки, ограничение экспорта и резервные копии наследуют
[стратегию защиты](../Task3/data-protection.md).

Минимизация выполняется до L1–L3. Для продольной аналитики, если она разрешена,
идентификатор заменяется отдельным случайным токеном для цели/набора, чтобы
нельзя было объединить все домены по общему ID. Служебная связь для исправления
и прекращения обработки хранится отдельно в защищённом реестре владельца,
недоступном обычному аналитику. Её наличие означает псевдонимизацию.

Сроки задаются по цели и типу, неизвестная политика срока блокирует публикацию.
В реестре происхождения фиксируются все производные версии, витрины и модели.
По запросу на исправление/прекращение обработки они блокируются, пересчитываются
или удаляются с учётом оснований хранения. Доступ к обученной модели проверяется
отдельно: очищенный набор не гарантирует отсутствие запоминания данных.

## Метрики эффективности классификации

Для оценки нужен размеченный контрольный корпус: реальные форматы источников
в закрытой среде, русскоязычные поля, опечатки, редкие классы и отдельный
набор новых схем. Владелец данных и ответственный за защиту подтверждают метки.
Тестовый корпус отделён от данных подбора правил; иначе результат завышен.
Синтетические примеры полезны для крайних случаев, но не заменяют эту проверку.

Оценка ведётся по каждому тегу на уровне поля/фрагмента и на уровне пакета.
TP — правильно найденный чувствительный объект; FN — пропущенный;
FP — ошибочно помеченный; TN — правильно распознанный нечувствительный.
Для нескольких тегов каждый оценивается отдельно.

| Метрика | Расчёт / смысл | Как помогает оптимизировать |
| --- | --- | --- |
| Recall — полнота, отдельно `HEALTH`, `IDENTITY`, `SECRET` | `TP / (TP + FN)`; если примеров класса нет, значение не определено | Указывает, где добавить словарь/детектор или усилить закрытый режим; нельзя заменить средним по всем классам |
| Precision — точность | `TP / (TP + FP)`; при отсутствии срабатываний не объявлять 100% | Показывает лишний карантин; улучшать контекст правил, сохраняя полноту критичных классов |
| F1 и матрица ошибок | `2 × precision × recall / (precision + recall)`; переходы между истинным/предсказанным классами | Сравнить версии детекторов, найти смешение `INTERNAL` и `HEALTH`; F1 не заменяет оценку пропусков |
| Качество опубликованного выхода | Число запрещённых фрагментов в проверенной выдаче / число проверенных фрагментов | Проверяет весь конвейер, а не только детектор; найденная утечка останавливает публикацию и отзывает версию |
| Покрытие и неопределённость | Доля фактически проверенных полей/строк; `UNKNOWN` и карантин / все поступившие пакеты | Обнаружить новые форматы и недостаток правил; снижение карантина не является успехом, если выросли пропуски |
| Структурные изменения | Новые fingerprints / пакеты; доля распознанных контролируемых изменений, время от нового поля до решения | Управлять очередью ручной проверки и версиями контрактов; проверить переименование/вложенные поля |
| Происхождение и политика | Опубликованные версии с полным источником, целью, владельцем и сроком / все опубликованные версии | Требуется полное покрытие; неполный манифест блокирует новую публикацию |
| Время решения и стоимость проверки | p95 времени в карантине, доля ручных решений, CPU/память/время на ГБ по формату | Распределить работу операторов и отдельные пулы OCR/текста; не ускорять путём отключения проверки |

Первая версия допускается при отсутствии пропусков в обязательных критичных
сценариях и запрещённых данных в проверенной опубликованной выдаче; метрики
полноты на репрезентативном корпусе имеют заранее утверждённые пороги по классу.
В качестве исходной цели предлагается recall ≥ 99% для критичных классов,
но это не подтверждённая точность и не гарантия отсутствия утечки.
Редкие классы и размер корпуса оцениваются отдельно; отсутствие ошибок
на маленькой выборке не доказывает безопасность на всём потоке.

В эксплуатации контролируются доля новых схем, карантин, исправления оператора
и проверенная выборка опубликованных версий. Это обнаруживает drift — изменение
характера входных данных. Новая версия правила сравнивается с предыдущей
на сохранённом корпусе и в закрытом параллельном прогоне до включения.
Анонимность требует отдельной оценки повторной идентификации; одной precision/recall
распознавания полей для этого недостаточно.

## Масштабирование

Приём и координаторы не хранят локальное состояние и масштабируются экземплярами.
Большие объекты находятся в S3; через реестр заданий передаются ссылки, хэши
и параметры. Анализаторы и преобразователи масштабируются отдельно;
число работников ограничивается доступной нагрузкой БД, хранилища и KMS.
Одно большое задание делится на блоки с манифестом частей; публикация ждёт
все части. Нельзя публиковать «готовые 90%» без явного нового производного набора.

Структурированные таблицы, свободный текст и OCR получают разные пулы ресурсов.
Чтение потоковое; размер распакованного файла, число ячеек, время и память
ограничены. Ошибка парсера или большой файл изолируются в одном задании.
Каждый источник имеет квоту, а интерактивные медицинские процессы — приоритет
над аналитическим импортом. Backpressure — ограничение приёма/скорости,
когда обработка не успевает, — не позволяет бесконечно накапливать очередь.

Метрики нагрузки: пакеты/строки/ГБ в час по формату, возраст старейшего задания,
p95 длительности пакета, количество повторов/отказов, загрузка CPU/памяти,
задержка и частота запросов сервиса выдачи,
время I/O (ввода/вывода), задержка KMS и скорость публикации. В метках нет
ID пациента, найденного значения или токена заказа.

Для планирования измеряются входная скорость `λ` и скорость работника `μ`
на представительной смеси форматов. Начальная оценка числа работников:
`N ≥ λ / (μ × u)`, где `u < 1` — выбранная допустимая доля загрузки с запасом.
Это приближение; проверяется ограничение общих БД/диска/ключей и долгих файлов.
Для окна пакетного обновления дополнительно измеряется время обработки всего
накопленного объёма, включая преобразование, проверку и публикацию.

При 5× объёме сначала увеличить число независимых работников и квоты закрытого
хранилища, разделить задания по источнику/времени, затем по замерам масштабировать
реестр, публикатор и аналитическую БД. Координатор использует конкурентно безопасное
получение заданий; повторная доставка считается нормальной и обрабатывается
идемпотентно. При ограничении реестра допускается выделить брокер задач,
но он не снимает необходимость состояния, проверок и контроля повторов.
Рост числа пользователей аналитики обрабатывается отдельно: квоты запросов,
агрегированные витрины и изоляция BI/ML от импорта и операционной БД.

## Приёмочные сценарии и открытые решения

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Добавить колонку, поменять тип, переименовать поле или вложенный путь | Обнаружена новая структура; классификация пересчитана, публикация не наследует прежнее разрешение |
| Поместить телефон/диагноз в `note` при прежней структуре | Детектор или закрытый режим свободного текста блокирует публикацию; проверка не ограничена заголовком |
| Неизвестный формат, макрос, большой архив, повреждённый документ | Карантин/отказ; никакой код источника не выполняется; остальные задания работают |
| Повторить пакет и завершить старое задание после истечения lease | Одна принятая версия результата; поздний работник не перезаписывает состояние |
| Отказать между загрузкой и активацией | Нет частичной выдачи; старая опубликованная версия доступна; повтор завершает текущую версию |
| Попытаться читать L1/Q0 ролью обычного аналитика | Отказ с аудитом; прямой SQL/объектная ссылка не обходит права |
| Подмешать прямой ID в L2, секрет в L1 или редкую группу в L3 | Активация запрещена; классификация и политика слоя проверяют выход |
| Изменить цель, отозвать разрешение, исправить источник | Новая обработка и выдача заблокированы/пересчитаны; производные версии найдены по происхождению |
| Поток 5× и параллельный BI | Очередь и время обновления остаются в согласованном окне; медицинская запись не деградирует от импорта |

Не заданы реальные схемы/форматы, размеченный корпус, скорость поступления,
порог повторной идентификации, бюджет обновления BI и нормативные сроки.
До реализации необходимо собрать закрытый контрольный корпус, назначить
владельцев классов/целей, подобрать правила и параметры по формату, проверить
публикацию целой версии на выбранных хранилищах и измерить 1×/5× поток.
Расширение на новые форматы или модели не может автоматически ослабить защиту
старых данных; каждая версия решений остаётся воспроизводимой.
